1. Вас пригласили настроить мониторинг на проект. На онбординге вам рассказали, что проект представляет из себя 
платформу для вычислений с выдачей текстовых отчетов, которые сохраняются на диск. Взаимодействие с платформой 
осуществляется по протоколу http. Также вам отметили, что вычисления загружают ЦПУ. Какой минимальный набор метрик вы
выведите в мониторинг и почему?

**Ответ:**

Для платформы вычислений с HTTP-взаимодействием и сохранением отчетов на диск минимальный набор метрик:

1. **CPU usage (user/system/iowait)** - так как вычисления загружают ЦПУ
2. **Memory usage (used/available)** - для контроля потребления памяти
3. **Disk I/O и свободное место** - так как отчеты сохраняются на диск
4. **HTTP response codes (2xx, 4xx, 5xx)** - для мониторинга доступности сервиса
5. **HTTP response time** - для контроля производительности
6. **Request rate (RPS)** - количество запросов в секунду
7. **Inodes usage** - важно при сохранении множества файлов

**Почему именно эти метрики:**
- CPU показывает нагрузку от вычислений
- Disk I/O и место критичны при записи отчетов
- HTTP метрики показывают доступность сервиса для клиентов
- Memory влияет на стабильность работы

6. **Report Generation Time** - время генерации отчета
7. **Queue Length** - длина очереди задач

**Визуализация:**
- Dashboard с "светофором" (зеленый/желтый/красный)

очередь хотят видеть все ошибки, которые выдают их приложения. Какое решение вы можете предпринять в этой ситуации, 
чтобы разработчики получали ошибки приложения?

**Ответ:**

Варианты решений:

1. **Standard Output + Docker logs**
   - Настроить вывод ошибок в stdout/stderr
   - Использовать `docker logs` для просмотра
   - Плюсы: не требует инфраструктуры

2. **rsyslog/syslog-ng**
   - Встроенные в Linux системы
   - Бесплатные, уже установлены

3. **EFK Stack (Elasticsearch + Fluentd + Kibana)**
   - Open-source решение
   - Fluentd легче чем Logstash

4. **Loki + Promtail + Grafana**
   - Легковесное решение от Grafana Labs
   - Хорошо интегрируется с Prometheus

5. **Graylog Open**
   - Бесплатная версия с базовым функционалом

**Рекомендация:** Начать с **stdout + docker logs** для разработки, затем внедрить **Loki** для production.

4. Вы, как опытный SRE, сделали мониторинг, куда вывели отображения выполнения SLA=99% по http кодам ответов. 
Вычисляете этот параметр по следующей формуле: summ_2xx_requests/summ_all_requests. Данный параметр не поднимается выше 
70%, но при этом в вашей системе нет кодов ответа 5xx и 4xx. Где у вас ошибка?

**Ответ:**

**Проблема:** Формула `summ_2xx_requests/summ_all_requests` не учитывает **3xx коды** (редиректы).

Если в системе есть 3xx коды, но нет 4xx и 5xx, то:
- `summ_all_requests = 2xx + 3xx`
- SLA = `2xx / (2xx + 3xx)`

**Пример:**
- 2xx requests: 700
- 3xx requests: 300
- Total: 1000
- SLA = 700/1000 = 70%

**Решение:** 
Правильная формула должна учитывать успешные коды:
```
SLA = (2xx + 3xx) / all_requests
Или исключить 3xx из подсчета:
SLA = 2xx / (2xx + 4xx + 5xx)
```

5. Опишите основные плюсы и минусы pull и push систем мониторинга.

**Ответ:**

**Pull система (Prometheus):**

**Плюсы:**
-  Центральный контроль сбора метрик
-  Легче обнаружить недоступные target'ы
-  Нет необходимости настраивать firewall для исходящих соединений
-  Проще масштабировать collectors

**Минусы:**
-  Сложнее мониторить ephemeral объекты (контейнеры, функции)
-  Target должен быть доступен из Prometheus
-  Проблемы с NAT/firewall

**Push система (StatsD, InfluxDB):**

**Плюсы:**
-  Легко мониторить ephemeral объекты
-  Работает через NAT/firewall
-  Application контролирует когда отправлять метрики

**Минусы:**
-  Нет контроля что target жив
-  Может потерять метрики при падении receiver
-  Сложнее отлаживать

**Гибридные:** Telegraf (может и pull, и push)

9. Изучите список [telegraf inputs](https://github.com/influxdata/telegraf/tree/master/plugins/inputs). 
Добавьте в конфигурацию telegraf следующий плагин - [docker](https://github.com/influxdata/telegraf/tree/master/plugins/inputs/docker):
```
[[inputs.docker]]
  endpoint = "unix:///var/run/docker.sock"
```

Дополнительно вам может потребоваться донастройка контейнера telegraf в `docker-compose.yml` дополнительного volume и 
режима privileged:
```
  telegraf:
    image: telegraf:1.4.0
    privileged: true
    volumes:
      - ./etc/telegraf.conf:/etc/telegraf/telegraf.conf:Z
      - /var/run/docker.sock:/var/run/docker.sock:Z
    links:
      - influxdb
    ports:
      - "8092:8092/udp"
      - "8094:8094"
      - "8125:8125/udp"
```

После настройке перезапустите telegraf, обновите веб интерфейс и приведите скриншотом список `measurments` в 
веб-интерфейсе базы telegraf.autogen . Там должны появиться метрики, связанные с docker.
